# V03 · 데이터 및 검토 계약

[제품 기준](README.md)을 따른다. 내부 구조는 실제 협찬 workflow를 지원하고 초기 사용자 UI를 복잡하게 만들지 않는다.

## 도메인

| 도메인        | 책임                                                        |
| ------------- | ----------------------------------------------------------- |
| Collaboration | 브랜드/캠페인, 협찬 상태, 컨택 일자, 공통 메모              |
| Content       | 개별 제작물, 플랫폼, 콘텐츠 링크, 광고 코드, 성과           |
| Task          | 제작·가편 전달·수정·컨펌·업로드의 할 일과 기한              |
| Source        | 원본 텍스트·스크린샷·가이드 참조                            |
| Constraint    | 필수/금지 제작 조건, 플랫폼, usage rights, retention period |
| Review        | 원래 후보, 정보 상태, 수정/확인, 근거 및 결과               |
| Import        | 저장 준비·중복 방지·이미지 staging 상태; 최종 협찬과 구분   |

한 협찬에 여러 콘텐츠/원본이 연결될 수 있다. 기본 UI는 협찬 상세 한 화면으로 시작한다. 가편/업로드 예정 날짜는 Task의 의미 있는 기한이며 다른 곳에 중복 저장하지 않는다. 컨택 일자는 가져온 시점에서 추정하지 않는다. 실제 게시와 협찬 완료는 구분한다.

## 정보 상태와 검토 상태

두 축은 독립이다.

- 정보: `present` 값 있음 / `not_mentioned` 원문에 미기재 / `uncertain` 불명확·판독 불가.
- 검토: `unreviewed` 미확인 / `confirmed` 사용자 확인 / `edited` 사용자 수정.

추출 누락을 사용자 확인 없이 미기재로 확정하지 않는다. 아직 확인하지 않은 항목은 uncertain + unreviewed로 시작할 수 있다. 후보 변경은 다시 미확인이 되고, 사용자가 명시적으로 후보 확인을 해야 한다. 원래 값/상태와 수정 결과를 함께 남긴다. 수동 입력은 manual로 표시하고 존재하지 않는 원문 근거를 만들지 않는다. mock의 근거는 null이며 예시라는 사실을 보존한다.

모든 표시 후보는 현재 MVP에서 필수 검토 대상이다. 미기재/불명확으로 확인을 마칠 수 있지만, 해당 값을 최종 사실이나 확정 기한으로 사용하지 않는다. 미확인 상태가 하나라도 있으면 payload 구성과 서버 저장을 모두 거부한다.

## 날짜·조건

- 가편 전달/업로드/컨택/공개 유지 등 날짜 역할을 구분한다.
- 여러 날짜는 각각 검토한다. 연도는 자동 추정하지 않으며 날짜만 있는 입력에 임의 09:00/자정을 넣지 않는다.
- 현재 MVP는 날짜 단위 기한만 지원한다. 정확 시각/시간대 지원은 별도 계약과 검증 후 추가한다.
- 불명확한 날짜는 due_date=null이며 최종 일정 Task로 변환하지 않고 Review에 남긴다.
- “영상 필수”, “자막 필수”, “특정 썸네일 금지”, “플랫폼”, “최종 컨펌 후 게시”는 날짜 이외의 중요한 요구사항이다.
- 공개 유지 기간과 usage rights는 독립이다. 게시일 미확정이면 유지 종료일을 계산 확정하지 않는다.
- 조건마다 무조건 새 Task를 늘리지 않는다. 체크리스트와 지켜야 할 조건을 구분한다.

## 저장 경계

원본 입력 → 원본 미리보기 → 후보 수정/확인 → 명시적 최종 확인 → payload 생성 → 서버 재검증 → 저장.

확인 전 최종 도메인 행은 없다. 클라이언트가 임의로 DB 테이블에 직접 쓰지 못하게 한다. 서버는 auth.uid()에서 소유자를 정하고, 필수 후보/날짜/정보·검토 상태를 다시 검증한다. 불명확/미기재 값은 null로 보존하며 미확정 날짜 Task는 생성하지 않는다.

최종 Collaboration/Content/Task/Source/Constraint/Review는 단일 RPC 트랜잭션으로 생성한다. 요청 UUID의 동일 payload 재시도는 기존 결과를 반환한다. 다른 사용자/다른 payload의 UUID 재사용은 거부한다.

Storage bytes는 DB 트랜잭션과 별개다. 비공개 manifest 경로에 staging하고 이미지가 준비된 뒤 commit한다. 실패 시 최종 행 전체 rollback, 저장 상태 확인, 원자적 abort 후 이미지 보상 삭제를 수행한다. 응답 유실이 성공인지 모르면 파일을 삭제하지 않고 같은 요청으로 확인한다. 브라우저 종료/삭제 실패의 임시 파일은 다음 로그인에서 재정리하며 그 한계를 명시한다.

V03 전용 프로젝트·소유자 RLS·관계 FK·비공개 Storage를 사용한다. 원문/이미지/광고 코드/성과를 analytics에 넣지 않는다. service-role key를 브라우저에 넣지 않는다. 원격 migration은 사용자가 별도 지시하기 전 실행하지 않는다.
